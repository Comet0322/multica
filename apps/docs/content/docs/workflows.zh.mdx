工作流是一个可复用的模板：由若干**节点**和一个**监督者**智能体组成，每个节点由一个现有的[智能体](/agents)执行。把任务分配给工作流就会启动一次**运行**。Multica 按依赖顺序调度节点，只有遇到需要判断的情况，监督者才会介入。

工作流解决的是有哪些步骤、按什么顺序的问题。[小队](/squads)是让 leader 在运行时决定交给谁；工作流则是事先把步骤定好。

## 创建工作流

在侧边栏打开**工作流**，点击**新建工作流**。填写名称并选择监督者智能体。创建后会进入**节点**标签页，在这里添加步骤。

每个节点有以下设置：

| 设置 | 作用 |
|---|---|
| **标题** | 步骤名称。标识（1–40 个小写字母、数字、`-` 或 `_`）由标题生成，可以修改。 |
| **智能体** | 执行这一步的智能体。 |
| **依赖于** | 必须先完成的节点。会形成环的选项不会出现。 |
| **审核** | 开启后，下游步骤开始前由监督者审核这一步的结果。 |
| **最大尝试次数** | 这一步最多运行几次，1 到 10（默认 3）。 |
| **提示词** | 这一步的指令，最多 20,000 字节。 |

工作流本身有**最大回退次数**（0 到 10，默认 3），即一次运行最多可以退回到之前步骤的次数。

一个工作流最多 50 个节点。修改只对新的运行生效；进行中的运行继续使用启动时的定义。

## 运行工作流

分配任务的方式与分配给智能体或小队相同：把任务分配给工作流。你需要有权调用工作流里的每个智能体，包括监督者。

运行启动时，Multica 会：

1. 为每个节点创建一个**子任务**，标题为 `<任务标题> · <节点标题>`，分配给该节点的智能体，父任务是你的任务。
2. 把你的任务移到 `in_progress`。
3. 启动所有依赖已满足的节点。

节点完成后，它的子任务会变成 `done`（或 `in_review`），这样后面的节点才能开始。每个步骤的智能体都会收到一份简报，包含上游步骤的结果，不必重读整段讨论。

任务处于 `backlog` 时不会启动运行；和其他分配对象一样，任务离开 `backlog` 时才启动。

一个任务同一时间只有一次进行中的运行。运行结束后想再跑一次，重新分配即可。

## 监督者做什么

监督者从不亲自完成某个步骤。只有以下情况会唤醒它：

- 标记了**审核**的步骤完成；
- 步骤失败，或智能体没有完成就结束；
- 步骤智能体因为上游结果有误而请求**回退**；
- 所有步骤都完成，需要写最终总结；
- 你在父任务下发表评论（见[和监督者对话](#和监督者对话)）。

每种情况下，它对该步骤做出一个决定：

| 决定 | 效果 |
|---|---|
| **通过** | 接受结果，步骤变为 `done`。 |
| **重做** | 带着反馈重新运行该步骤（尝试次数未用完时）。 |
| **重试** | 不带改动重新运行该步骤（尝试次数未用完时）。 |
| **跳过** | 取消该步骤的任务；下游步骤视其为已满足。 |
| **回退** | 退回到之前的步骤（当前步骤本身或其上游），并重新运行其后的所有步骤。消耗一次回退。 |
| **升级** | 把决定交给人。 |
| **中止** | 以失败结束这次运行。 |

如果监督者连续两次结束时都没有给出有效决定，该步骤会自动升级给人。

所有步骤都是 `done` 或已跳过后，监督者会在父任务下发布总结，父任务随即进入 `in_review`，运行完成。请审阅后自行把任务标记为 `done`。

## 由人来决定

打开父任务。侧边栏的**工作流运行**面板显示每个步骤的状态、智能体和尝试次数，附带指向子任务的链接，以及事件时间线。

需要你处理的步骤会标记为**等你处理**并显示原因。发生升级时，你还会收到一条收件箱通知**工作流需要你来决定**，点击后打开父任务。步骤有了决定或运行结束后，这条通知会自动归档。

面板提供**通过**、**重做…**、**重试**、**跳过**、**回退到…**和**中止…**。重做和回退需要填写给智能体的反馈；中止需要填写原因。用完**最大尝试次数**后无法重做或重试，用完**最大回退次数**后无法回退。如果你决定的过程中步骤状态已变化，Multica 会提示你查看最新状态后重试。

**取消运行**会停止运行中的步骤，并取消未完成的步骤任务。

触发运行的成员、工作流创建者和工作区管理员可以对运行做决定或取消运行。创建者和管理员可以编辑或归档工作流。

### 和监督者对话

在父任务下发表评论且不 `@` 任何人，监督者就会回复。它也可以代你操作：如果你让它通过或重做某个步骤，它会以你的名义提交决定，前提是你本人有权这样做。`@` 提及的行为不变，会触发你点名的智能体。

## 决定块

智能体通过评论汇报决定，评论里带一个围栏代码块。先把评论写入文件，再用 CLI 发布：

````bash
# decision.md 的内容：
# 看起来没问题。
#
# ```ext-workflow
# action: approve
# ```
multica issue comment add <issue-id> --content-file ./decision.md
````

代码块是 YAML：

````text
```ext-workflow
action: rewind
step: backend
to: spec
reason: 规格假设接口是分页的，实际不是。
feedback: |
  改用游标分页，并更新数据流部分。
```
````

| 字段 | 用途 |
|---|---|
| `action` | `approve`、`redo`、`retry`、`skip`、`rewind`、`escalate`、`abort` 或 `request-rewind`。 |
| `step` | 步骤的节点标识。发在父任务下时必填，`abort` 除外。 |
| `to` | 要退回到的节点。`rewind` 必填，`request-rewind` 可选。 |
| `reason` | `escalate`、`abort` 和 `request-rewind` 必填。 |
| `feedback` | `redo` 和 `rewind` 必填。 |

评论发在哪里，决定了谁可以发：

| 作者 | 评论位置 | 允许的操作 |
|---|---|---|
| 监督者，处理审核、失败或回退请求时 | 该步骤的子任务 | 除 `request-rewind` 外全部 |
| 监督者，处理对话时 | 父任务，带 `step` | 除 `request-rewind` 外全部，前提是发评论的人有权决定 |
| 步骤智能体，该步骤运行期间 | 它自己的子任务 | 仅 `request-rewind` |

一条评论只能带一个代码块，未知字段会被拒绝。无效的代码块会在同一任务下收到一条说明错误的回复，并在时间线里记录一条**协议错误**。人发的代码块会被忽略；人通过运行面板做决定。

只有在引擎开启、且任务是某个工作流的父任务或步骤任务时，这个代码块才算协议内容，不会唤醒任何智能体。在其他任务上，它只是普通文本。

## 限制

| 限制 | 数值 |
|---|---|
| 每个工作流的节点数 | 50 |
| 每个节点的提示词 | 20,000 字节 |
| 每个节点的最大尝试次数 | 1 到 10 |
| 每个工作流的最大回退次数 | 0 到 10 |
| 每个任务进行中的运行 | 1 |

## 关闭引擎

自托管服务器可以通过环境变量 `MULTICA_WORKFLOW_ENGINE` 关闭工作流运行。默认值为 `true`，设为 `false` 即关闭引擎。

关闭期间，把任务分配给工作流会被拒绝，运行的决定和取消也会被拒绝。工作流和运行仍可创建、编辑和查看。参见[环境变量](/environment-variables)。

<Callout type="info">
引擎关闭时已在进行的运行不会继续推进，直到重新开启。
</Callout>
