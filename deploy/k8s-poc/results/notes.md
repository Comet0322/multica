- T3b FINDING (GAP-3, blocker for "N replicas share one runtime"): a duplicate pod with the same MULTICA_DAEMON_ID was started then deleted (SIGTERM). Its graceful shutdown calls /api/daemon/deregister, which takes the SHARED runtime offline. The surviving replica keeps heartbeating but the server logs `preserved_offline=1` and never flips it back; a task queued afterwards stayed `queued` (ClaimAgentTask requires runtime status=online). Only a re-register (pod restart) recovers it.
  - Consequence: scale-down of any replica stalls the whole shared runtime. Viable alternatives: one daemon_id per Sandbox (project-scoped; suspend/resume is then legitimate offline->online via re-register, see T4), or a managed mode that skips deregister on shutdown.
